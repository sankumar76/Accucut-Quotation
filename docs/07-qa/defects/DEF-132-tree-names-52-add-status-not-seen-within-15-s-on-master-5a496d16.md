## Leads (not findings; step 1 is lane 1's)
`src/lib/estimates/row-name.ts` `addedAnnouncement(before, after, addedId)` builds the text (it returns an **empty string when the added node is not in `after`**, appends ' 1.2 is now a Sub-part.' when the add made an earlier Part a Sub-part, and takes the kind word from the tree); `src/components/features/estimate-workspace/use-parts-tree.ts` (about line 233) calls `setAnnouncement(addedAnnouncement(before, answer.nodes, answer.nodeId ?? ''))` after the server's answer. Questions: when exactly is the status written (after the answer, after the tree re-read), into which live region, and can an existing message in that region make the same text not re-announce or not appear; is there a path where the answer carries no `nodeId`, or the added node is not in `answer.nodes`, so the status is silently empty.

## Step 1 posted by lane 1 on #802 (relayed by the orchestrator, 2026-11-27; QA read the comments and the run log; test plan 0.3.91)
**Code reading (lane 1, nothing run):** the add status is written **after the server's answer, in the same synchronous step as the tree** (`use-parts-tree.ts` `addUnder` -> `change()` -> `settle`: `setNodes(answer.nodes)` then `onDone(answer)` -> `setAnnouncement(addedAnnouncement(...))`), into one `<p role="status" class="sr-only">` in `TreePanel`; the state is one string, so **a second identical text in a row is a React no-op and would not be re-announced (a real 4.1.3 weakness, but only for a second identical add; the case adds once)**; the `TREE_CHANGING` 300 ms line cannot overwrite the result; `addedAnnouncement` returns an empty string only when the added row is not in the answer's nodes, which the server's 200 answer always has. Lane 1 names where the status could be missing: the add was not sent (a menu choice dropped by `change()` while another change is in flight, or by the leave guard), the request failed or was refused (a danger notice, no status), a region remounted, or the text replaced; **no cause is claimed**.
**The diagnostic run (PR #803, a draft, diagnostic only; run 45847511614, head `89937cc3`, `pull_request`, created 15:16:59Z, `failure`; shard 4 job 140004908721; QA read the log):** shard 4 `2 failed, 1 flaky, 22 skipped, 571 passed (13.5m)`, **draw 0.65 against 31015cce (324 tests; a fast draw)**. `estimate-tree-names.spec.ts:52` [desktop] **failed attempt 1 and the retry** (`Test timeout of 30000ms exceeded` in `locator.click` on 'Add under 1.1', **before the status wait**); `estimate-tree.spec.ts:901` [desktop] failed both attempts; `:1065` failed attempt 1 and passed on retry; **40 'intercepts pointer events' lines** (a row link `<a href="#estimate-form-area-title">`, the branch-arrow `<span>`, a row icon `<path>`); no `form[data-part-form]` line. The diagnostic, both `:52` attempts: **no request `POST nodes`, no answer, no FAILED: the add request was never sent**; the only status text on the page was the form's save line; at the end '0 elements hold "Added 1.1.1 Part"'. **So on that run the status was not missing after an add: there was no add; the cause is DEF-129's pointer interception (the click never reached the button).** Lane 1 says that the red on `master` `5a496d16` (status not seen within 15 s, no interception line) may or may not be the same; **one run cannot tell**, and the case passes on tablet and mobile (no hover there). Lane 2 is measuring whether the hovered row's toolbar moves the rows below it (a product fault if so: a real user could click the wrong row). **QA's reading:** the two `:52` failures of 26 Nov that had an interception are DEF-129's; the `5a496d16` failure stays unexplained (its attempt 1 has no trace, and the retry passed); **DEF-132 stays open until a status-not-seen failure is read again with the diagnostic on, or master closes it as a duplicate of DEF-129 on the evidence.** The interception was at a **fast draw (0.65)**, so it is not a slow-runner effect.

## Lane 2's measurement of the row shift (2026-11-27, relayed; test plan 0.3.92)
**Lane 2's measurement (relayed by the orchestrator, 2026-11-27; QA did not run it) on `master` `d2b58f04`, real Chromium, 1366x768, fine pointer, a 5-row tree:** hovering a row shows its toolbar line (**38 px plus a 4 px margin**), which **pushes every row below it down 42 px**. Moving the pointer from row 1.1 (toolbar shown) **straight down onto row 1.2's link, 1.2's link slides 42 px up, above the pointer, and the pointer lands on 1.2's own toolbar: `elementFromPoint` returns 'Add fastener under 1.2'** (a real user would press the wrong row's button). With a still pointer and a visible toolbar the buttons are hit correctly. **This is the product fault DL-426 named:** the ruling's check ('moving down onto a row's toolbar keeps it', 'one toolbar at a time with no flicker') passed on `744a8fa5` with a slow 3 px pointer, and **the measurement with a normal pointer shows the rows moving under it, so the hand check fails.** **Meaning for this Bug:** the 'status not seen' failure of `5a496d16` may be the same fault (a menu item or button pressed on a row that had moved), which would make DEF-132 a duplicate of DEF-129; **one run cannot tell**, and the failed attempt left no trace. **Master is to rule on grade and on whether to merge DEF-129 and DEF-132 into one record** (pending, DL number to come). Until then DEF-132 stays open with its step 1 (lane 1's diagnostic on #803 already showed no add request was sent in the interception case, so the status was not missing after an add).
