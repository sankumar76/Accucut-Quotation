## Security checks (the brief's focus list)

| # | Check | Result |
|---|---|---|
| 1 | **Token entropy and form** | **Verified.** `randomBytes(32)` → 43 characters of base64url (`reset-token.ts:35`). A shape check (`^[A-Za-z0-9_-]{43}$`) stops anything else before the database. 256 bits, so a fast hash is right and there is no use-attempt limit (correctly argued in the Dev Record) |
| 2 | **Hash at rest** | **Verified.** Only `sha256(token)` as 64 lower-case hex digits is stored. `CHECK (token_hash ~ '^[0-9a-f]{64}$')` and a UNIQUE index (migration lines 24 and 35). The integration test reads the table and the outbox after the send and does not find the token. The raw token exists only in the e-mail, the link and the outbox body until the row is sent, failed or skipped |
| 3 | **Single use under parallel posts** | **Verified.** The claim is one `UPDATE … FROM users … WHERE token_hash = $1 AND used_at IS NULL AND expires_at > $now AND u.is_active RETURNING user_id` (`password-reset-repository.ts:90-94`). Under READ COMMITTED, a second post waits on the row lock and re-checks `used_at IS NULL`, so 0 rows match. The integration case holds two posts that have both read the link, then releases them: exactly one 204, the other 400, and `session_version` raised once. **The constant-time deviation is sound:** no secret is compared in application code, and the lookup is by a hash the caller cannot choose |
| 4 | **Expiry** | **Verified.** `expires_at = now + 60 min`, and the claim needs `expires_at > now` (`findUsable` too). It is tested at 59:59.999 (works) and 60:00 (refused). The outbox `send_before` is the token's expiry, so a late row is skipped `EXPIRED` and blanked |
| 5 | **Older tokens on a new request; others after a reset** | **As the AC says.** A new request does **not** invalidate earlier links. AC-6 does not ask for that, and all of them go to the same mailbox. A successful reset marks every other unused link of the person used in the same transaction (`invalidateOthers`), and this is tested. Links are **not** invalidated by an Admin reset, an own change, a hand-over or a deactivate-then-reactivate (#558, judged in SQR-04) |
| 6 | **Enumeration: status, body, headers** | **Verified.** The route always answers `{message}` 202. The decoy path (`simulateIssue`) runs for unknown and deactivated people. `FEATURE_EMAIL` off creates nothing for anyone (D-1). The security test compares status, body and header set byte for byte across known, unknown, deactivated, other letter case and the flag off (only the request ID differs). The 429 is the same for known and unknown. Five kinds of bad token give one 400 |
| 7 | **Enumeration: timing class** | **Same shape, one residual difference** (SQR-01). Both paths do one lookup, one token, one render and a transaction of two statements. But the real path's two writes (index maintenance, FK check, and a WAL flush at commit) are not the decoy's two `SELECT 1` and read-only commit. On a LAN install, the difference can be larger than the jitter. The rate limits and the mail the person receives make it hard to exploit |
| 8 | **Rate limits per address and per typed e-mail** | **Verified as specified** (5 per 15 min each; HMAC-SHA-256 keys under `AUTH_SECRET`; own kinds `reset-request` and `reset-address`, so they never block sign-in or step-up). The address is counted before the e-mail and gets its place back on an e-mail refusal or a fault of ours. **Shared office:** yes, one person can use up the address counter for everyone behind the same address, and on an install without the proxy every caller shares the `unknown` counter while a forged `X-Forwarded-For` escapes it (SQR-02, Minor: only availability is affected; the Admin's reset remains) |
| 9 | **Sessions and password policy** | **Verified.** `setPasswordFromReset` in one statement: new argon2id hash, `must_change_password` cleared, `session_version + 1`, active people only, in the claim's transaction. A person deactivated between the claim and the write rolls the whole transaction back (tested). The rule is the shared `assertPasswordRule` with the person's e-mail and `subject: 'self'`. It runs **before** the claim, so a bad password keeps the link (AC-8, tested). The schema has a length ceiling. The sign-in block (and the step-up and change-form blocks) are lifted after the commit (SQR-06) |
| 10 | **Recipient (DL-262)** | **Verified.** The outbox row carries `to_user_id` only. The address is read from `users` at send time, active people only (`NO_RECIPIENT` otherwise, and blanked). The link is built from `APP_ORIGIN`. Tests with a hostile `Host` and `X-Forwarded-Host` show that no request value becomes an address or the origin |
| 11 | **Token and link never logged, never in audit or error bodies** | **Verified in the app.** `withPublicRoute` logs class, code, route and request ID only. The forgot route logs nothing. The reset writes one info line (`requestId`, `userId`). The integration log-capture case drives the real routes over PostgreSQL and finds no token, password, `$argon2` hash, e-mail or address in any line, and the audit table unchanged (A-2). The unit test shows no thrown error holds a secret. **Outside the app:** the token is in the query string, so a TLS proxy's access log can hold it (SQR-03) |
| 12 | **Reset-link body blanked** | **Verified** (09.01 and 09.06 code, no new code needed). The bodies of `password-reset` rows are emptied in the same statement that records sent, finally failed, skipped `EXPIRED` and skipped `NO_RECIPIENT`. All four paths are tested against PostgreSQL |
| 13 | **Public routes: CSRF, no auth bypass** | **Verified.** `withPublicRoute` accepts only a manifest row with `roles: 'public'`, and `withRoute` refuses a public row, both at module load. The origin check (`Sec-Fetch-Site: same-origin` or `Origin === APP_ORIGIN`) runs before the body is read. Both routes are in the csrf loop and in the "no unchecked state-changing route" rule. Neither route reads or issues a session. A signed-in visitor resetting another account's link changes only the token's person |
| 14 | **Headers** | **Verified.** API answers and problems: `Cache-Control: private, no-store`. Both pages: `private, no-store` and `Referrer-Policy: no-referrer` (`next.config.ts`), with `noindex, nofollow` from the layout. The proxy matcher now excludes both pages, so the token is never copied into the return-path header for a visitor who has a cookie. The E2E checks the headers and that no resource comes from another site |
| 15 | **Open redirect** | **None.** The e-mail link comes from `APP_ORIGIN` plus a fixed path. The pages link only to the fixed `/sign-in` and `/forgot-password`. There is no return or next parameter. GET never consumes the token, so a mail scanner that opens the link cannot burn it |
| 16 | **Lock-out interplay with sign-in** | **Sound.** Reset requests never count on the sign-in keys, and a sign-in lock-out never blocks a request. A successful reset clears the account key, as the Admin's reset does (FR-004). Someone who guesses passwords can lock again afterwards, as today |
| 17 | **#509 class (stale state used after a check)** | **Not repeated.** The password is set for the person **the claim returned** (not one read earlier), and "active" is checked inside the claim and again inside the update. The only value read before the transaction is the e-mail used for the rule and for the key cleared afterwards. E-mail addresses cannot be edited (`user-service.ts` has no e-mail change), so it cannot be stale. Tested by two cases named after #509 |

## Verdict

**APPROVE WITH COMMENTS.** There is no Blocker, Critical or Major finding. The §9 item 2 condition is met, and the merge waits only for every required check to be green on `e2aac7e1`.

- **Security holds for the threats that matter.** The token is 256-bit, only its hash is stored, it is single use under concurrency, and it expires exactly. Answers are byte-identical for every kind of address. The recipient comes from the database at send time. Every session ends after a reset. The shared rule is applied. No secret is in the app's logs, errors, answers or the audit. Bodies are blanked. The public routes have their origin check. The pages are not cached and send no Referer.

  - SQR-02: the `unknown` address bucket, the proxy requirement in AQP-38, and the per-address number, which needs a delivery-lead decision.
  - SQR-03: proxy access-log configuration.
  - SQR-04: add deactivation to #558.
