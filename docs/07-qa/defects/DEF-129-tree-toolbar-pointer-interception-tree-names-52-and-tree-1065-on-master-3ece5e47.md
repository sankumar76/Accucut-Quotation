## The ux-expert's no-shift toolbar ruling mapped (2026-11-27; `docs/03-ux/rulings/tree-toolbar-no-shift-2026-11-27.md` (records-u 7530e53f; checks TS-1 to TS-17); the ruling was not seen running: no browser, no code edited)
**The design:** a **reserved 40 px slot (`--tree-slot-h`) under every row that has a toolbar, for a mouse only**; the toolbar (38 px high; three 36 px buttons; same order, names and tooltips) shows **inside the slot** on hover (the pointer over the row **including its slot**), keyboard focus anywhere in the row, an open menu or the delete dialog, or a press; **when hidden it is `sr-only` (clipped to 1 px, in the tab order and the accessibility tree), never `opacity: 0`, `visibility: hidden` or `display: none`**; the empty part of a slot is not a control; nothing is drawn over another row; no animation; an optional 100 ms hide delay (never a show delay) is a polish, not the fix. **Touch is unchanged:** only the selected row has a toolbar and a 48 px slot (44 px buttons). **Stated exception (item 7):** on touch, **tapping another row moves the rows below the selected row** (the toolbar goes with the selection); the ruling does not count it as a layout shift because a tap is user input (the browser's own measure ignores a shift within 500 ms of a tap). **QA records it as the one accepted movement, and its CLS check (TS-4) is for hover and focus with a mouse, not for a tap.** The delivery lead may ask for a slot under every row on touch (94 px a row), which the ux-expert does not recommend. **Fallback S** (a slot only under rows the pointer has visited) is named and **not recommended**: rows below a visited row still move, so it does not meet constraint 1.
