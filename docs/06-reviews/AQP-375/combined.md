| SQR-01 | **Minor** | `deploy/windows/update.ps1:767` (stop), `:775` (migrate), `:795` (start and check); `tests/unit/windows-deploy-files.test.ts:884` | **An update's health check is passed by the old worker's last heartbeat, not the new one's.** Update stops both services, migrates (seconds), switches and starts, then polls `/api/health`. The newest `heartbeat` row is the one the **old** worker wrote just before the stop, usually well under 3 minutes old, so the first poll answers 200 as soon as the new app is up. A new worker that reaches "Running" but crashes or cannot write (for example a bad `.env` value it alone reads, or a node error at start) does not stop the update and triggers no rollback. Health then turns red within 3 minutes and the uptime monitor alerts, so nothing is lost and this is **not a regression**: before this PR, health did not look at the worker at all. But the new test's title says "the worker is started before the wait (its first heartbeat is written at start)", which suggests the wait proves the new worker; for update it does not. Restore is not affected: the restored copy's heartbeat rows are old, so there the wait does depend on the new worker, as the PR body says. Install is not affected: a fresh database has no heartbeat | In `Invoke-AccucutUpdate`, note `$startedAt = (Get-Date).ToUniversalTime()` just before `Start-AccucutServicesAndCheck`, and after a 200 also require a heartbeat newer than it, within the same allowance (psql with the migrate URL the script already holds: `SELECT count(*) FROM job_runs WHERE job = 'heartbeat' AND finished_at > '<startedAt>'`). ## Verdict

**APPROVE WITH COMMENTS.** There are no Blocker, Critical or Major findings, and all nine ACs are met.

- **Data loss:** `prune_heartbeat_runs()` can remove only heartbeat rows older than 7 days. It takes no argument, its path is pinned, its table is schema-qualified, the owner role owns it, `accucut_app` alone may execute it, and the runtime role still has no DELETE. This was proven on a real Windows install in Stage 13.
- **Log exposure:** no token, cookie, secret, message, stack, body, header value or query string reaches a log line or a `job_runs` row, and the decode and the hook cannot throw.
- **Health:** red within 3 minutes of a dead worker. Two Minor edges for the hardening window: **SQR-01** (update's check is passed by the old worker's last row) and **SQR-02** (a clock that steps back keeps it green).
- **Before merge:** a fully green required check on the head, with stage 11's integration tests included and any unexplained failure identified (**SQR-07**).
- **GitHub:** review submitted as COMMENT on PR #529 with inline comments on SQR-01 to SQR-05.
