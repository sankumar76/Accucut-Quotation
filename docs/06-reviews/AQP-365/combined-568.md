## Security and data-integrity checks

| # | Check | Result |
|---|---|---|
| 1 | **Validation parity:** `recordMany` cannot store what `record` would refuse | **Holds, by construction.** The whole body of the old `record` moved, unchanged, into one module-private function `checkedRow` (`audit-service.ts:145-171`). `record` is now `append(checkedRow(entry), tx)`, and `recordMany` is `entries.map(checkedRow)` and then `appendMany`. So the label lengths, the actor label, the object type, the zod `before`/`after` shapes and the secret scan are one code path. The row stored is built from the zod output (`before.data`, `after.data`), never from the raw input. An unknown event fails the same way in both, with a `TypeError` before any write (SQR-06). The unit tests prove a bad second `after` (`shape/after`), a hash in one entry (`secret/after.reason`), an empty label and a 201-character actor label each refuse the whole batch, with `appended` empty |
| 2 | **All or nothing** | **Holds.** (a) Every entry is checked before the repository is called: `map` throws on the first refusal, inside the async function, so it becomes a rejection and `appendMany` is never reached (unit test: `calls.batches` is `[]`). (b) The rows go through `clientFor(db, tx)`, the interactive-transaction client. A handle not opened by a runner is refused (unit test: `'did not open'`). (c) The chunks are written by sequential `await`s on the same client, inside one `withDatabaseErrors`, so every chunk is in the caller's transaction. The integration test writes 1,001 rows, throws, and finds no row of either statement. (d) A refused entry inside a real save rolls back the default, every customer and the log (integration test with a 201-character customer name) |
| 3 | **SQL safety** | **Safe.** `appendMany` is a Prisma tagged template. Each row is a `Prisma.sql` fragment with 9 bound values, and the rows are combined with `Prisma.join`. There is no string concatenation and no `$executeRawUnsafe`. `before` and `after` are bound as `JSON.stringify` text cast `::jsonb`. A JS `null` stays SQL NULL, the same as `jsonColumn` does for `append`. IDs are cast `::uuid`. `id` and `created_at` take the database defaults (`gen_random_uuid()`, `date_trunc('milliseconds', clock_timestamp())`, in the schema), so no code can back-date an entry. The integration test keeps quotes, a backslash and a literal `$1` intact and stores a creation's `before` as SQL NULL |
| 4 | **Bind-parameter limit** | **Safe.** There are 1,000 rows × 9 values = 9,000 parameters per statement. The limit with `@prisma/adapter-pg` 7.10.1 (node-postgres) is 65,535, and 9,000 is also under the conservative 32,767 that the code comment quotes (SQR-04). Integration proves exactly 1,000 rows go in one statement and 1,001 go in two (grouped by `cmin`). The service always makes one `appendMany` call, and only the repository chunks |
| 5 | **The static check still sees every write** | **Holds.** `AUDIT_WRITE_METHODS = new Set(['record', 'recordMany'])` is the only gate (`verdictOn`), and every rule after it does not depend on the name: `any` receiver, not a direct callee (`.call`, `.bind`, alias), placement, ownership of the handle along the chain, awaited. `isAuditServiceWrite` still requires the member to be declared on the `AuditService` interface in `audit-service.ts`, so a look-alike `recordMany` elsewhere is not counted. New cases: +1 passing (in a `.run(` callback) and +2 failing (a handle that is not the callback parameter: `NOT_A_PARAMETER`; not awaited: `NOT_AWAITED`), as ADR-018 asks. The count pin (15) still holds, because two `record` calls became two `recordMany` calls. The confidentiality pin is `['list', 'record', 'recordMany']`, and no method changes or removes an entry. The finding texts still say "record" (SQR-05) |
| 6 | **Audit content and request grouping** | **Verified.** The two loops became one `recordMany` each (`masters-service.ts:344`, `default-propagation-service.ts:151`). The rate's own `master.edited` is still a `record`, written first (`masters-service.ts:340`). `customerRateEntries` is unchanged, and every entry spreads the same `context`, so all entries of a step share the `request_id`. `process-propagation.test.ts` AC-9 still checks the exact entries (object, before, after, request ID) through the real batch path. Its helper now sorts, and says so, so no test asserts display order inside a request (ADR-018 item 4). Rows of one statement can share a millisecond. The list order `(created_at DESC, id DESC)` and its cursor stay correct, because `id` is unique |
| 7 | **SQR-02 (before value in Save choices)** | **Fixed in code.** `previous` now comes from `RETURNING ... u.shown::text`, and the `?? item.defaultValue` fallback that could never be right is gone. `u.shown` is the request text cast to `numeric`, and the row changes only when `cr.value = u.shown`. So the stored "before" is numerically the database value, in canonical spelling: `'01.50'::numeric::text` is `1.50`. The Dev Record's sentence "the text is still the request's spelling" is not quite right, because the cast drops the leading zero, which is the point of the fix. No test proves it (SQR-01) |

## Verdict

**APPROVE WITH COMMENTS.** There is no Blocker, Critical or Major finding, so the §9 item 2 merge condition is met.

- **No entry escapes validation.** `record` and `recordMany` share one check function, and every row stored is the zod-parsed form.
- **All or nothing holds.** Every entry is checked before the first write, the rows go through the caller's transaction client, and every chunk rolls back with the change.
- **The SQL is safe.** It is a tagged template with bound values and `::jsonb` casts, at 9,000 parameters per statement.
- **The static check keeps its reach.** It still refuses a `recordMany` that is not owned, not awaited, aliased or on an `any` receiver.
- **#568 / PRF-F-05 / the earlier SQR-01 are resolved.** The medians are 374 ms (the save) and 198 ms (Save choices) at 500 customers, against 500 ms. One `appendMany` per step is asserted.
- **Must be fixed before merge:** none.
- **Recommended before the squash (a few lines each):** SQR-01 (the `'01.50'` regression test for the SQR-02 fix), then SQR-03 and SQR-02. Otherwise they go to the hardening window as `tech-debt`.
- **Follow-ups:** SQR-04 to SQR-06 are wording or optional. SQR-07 goes to reviewer-performance to re-grade PRF-F-05.
