## Summary

**The fix is right, and it closes DEF-148 as reported.** The tree-following effect is gone. The revision a save sends now comes only from a snapshot whose values the form also holds: the seed, the load, the form's own saves and the conflict re-read. I checked every write of `heldRef` in `use-part-form.ts`. Each one now sets `revisionRef` from the same answer (load at `:149-150`, `send` at `:353-354`, `reconcile` at `:296-297`). So a tree re-read can no longer move what a save sends. The next save after another person's change gets the server's 409 (`estimate-node-repository.ts:131-132`, a conditional `UPDATE … WHERE revision = expected`), and `reconcile` runs. The S1 cases reproduce the Sev-1 shape on master and pass at head: two of the other person's fields, then Save draft, then a tab hide, then one 30-second tick, each checked on the server.

**One path still adopts a revision without its values (QLT-839-01, Major).** The picture guard (`saved.revision <= revisionRef.current + 1`) relies on a server rule: a real picture change raises the part's revision by exactly one, under the estimate lock (`image-service.ts:89-95`). But the server also answers a no-op (the same picture again) with its current revision and no write (`image-service.ts:122`). After another person's field change, that answer is exactly one ahead, so the form adopts it over values it has not seen. The next save then goes through with no 409, and the follow-on flushes send the stale texts back. This is the DEF-148 mechanism through the picture. It was there on master too, where every picture answer was adopted. The PR narrows it and names it as a known limit. The client can tell a no-op apart at no cost, so I recommend keeping the guard and tightening it.

**Own changes are safe, at the cost of one round trip.** After the person's own move of the open part (the server raises the moved part's revision, `estimate-service.ts:486-490`), the next save now gets a 409, re-reads, finds nothing changed and sends again. It is saved with no notice, which is what DL-472 (4) (d) asks for. But the ruling's own-move unit case is not in the PR, and neither is its E2E case (QLT-839-02). The extra round trip can lose a value typed just before the page closes (QLT-839-04, Minor). A save queued while a picture is uploading also gets a false 409, but that is not new (QLT-839-03, Minor, already on master).

**Merging with #836 and #811 is clean.** `git merge-tree` of this head with #836 (`484f55f2`) and with #811 (`6601023c`) gives no conflict. The merged file keeps one seed guard and no effect. With the guard, the starting revision is the same as before for an editable form. Without it, a stale seed now fails safe with a 409. But both branches' comments at the guard say that a save sends "the tree row's revision". After this PR that is false, and a clean merge will carry it over unseen (QLT-839-05).

**Security hygiene holds.** The change is client-only. No route, schema, authorization or role check is touched. The server is still the only judge (the conditional write). The tests use invented IDs and values. No secret, personal data or cost value is anywhere in the diff.

## Focus questions

**(1) Every save path sends the revision of the values the form holds.**

| Path | Revision sent | Result |
|------|---------------|--------|
| Field save (`commit` → `queueSave` → `send`) | `revisionRef` (`:339`) | One snapshot |
| Save draft (`sendAgain('draft')` → `commit`) | same | One snapshot |
| Tab hide / page leave (`sendAgain('leave')` → `autosaveField`) | same, keepalive | One snapshot. See QLT-839-04 for a 409 during a leave |
| 30-second tick (`sendAgain('auto')`) | same | One snapshot |
| Watchers (`syncWatchers` → `send`) | same | One snapshot |
| `resolveConflict('mine')` → `commit` | `reconcile`'s revision | One snapshot |
| Conflict re-read (`reconcile`) | sets `revisionRef` and `heldRef` from one answer (`:296-297`) | One snapshot |
| Load and Try again (`attempt`) | sets both from one answer (`:149-150`) | One snapshot. A load that lands after a newer own save sets an older pair, which fails safe with a 409 |
| Picture (`pictureSaved`) | adopts the answer's revision **without values** when it is at most one ahead | **Not one snapshot for a no-op answer (QLT-839-01)** |
| Own move or reorder (tree re-read) | not adopted any more | Fails safe: one 409 and a re-read, no notice (QLT-839-02 asks for the test, QLT-839-04 names the cost) |

**(2) No path silently overwrites any more, except QLT-839-01.** The server's conditional write turns any stale revision into a 409 `PART_CHANGED`, and `reconcile` makes the plan. The S1 cases show the notice logic is right: A and B are adopted with no notice (only the other side changed them), C is sent again, and the "row moved on" case shows the notice for the field both sides changed.

**(3) No false 409 after the person's own save:** `send` adopts its own answer (`:353`). **After a picture change:** none, unless a save was queued while the picture was uploading (QLT-839-03, already on master). **After an own move:** one 409 every time, saved with no notice. It is benign while the page is open (QLT-839-04).

**(4) The "at most one ahead" heuristic.** It relies on three server facts: (i) a real picture change raises the part's revision by exactly one, in the same transaction as the estimate lock, conditional on the revision it read (`image-service.ts:89-95`, `estimate-node-repository.ts:141-144`); (ii) `inTurn` runs the picture after every save this form has queued, so the form's revision is the server's at that moment unless someone else wrote; (iii) a no-op (the same bytes, or removing a picture that is not there) writes nothing and answers the current revision (`image-service.ts:122, 137`). Facts (i) and (ii) make "one ahead" mean "only my change" for a real change. Fact (iii) breaks it: after another person's field change (R → R+1), re-sending the identical picture answers R+1, which looks like the form's own change. A no-op remove is safe, because the control can only offer Remove while the form's snapshot has a picture, so a server with none means someone else removed it (+1), and any field change on top makes it R+2. **Recommendation: keep the guard and tighten it (QLT-839-01).** Adopt only when this request changed the picture and the answer is exactly one ahead. Not adopting is always safe, because it costs at most one 409. Dropping the guard would bring back every picture case. A stronger design, with the form's revision as an `If-Match` on the picture routes, changes the route contract during the freeze. It is not needed for this PR.

**(5) The seed guard (#836 `484f55f2`, #811 `6601023c`).** They are complementary, as DL-475 (4) says. With the guard, an editable seed is used only when `parsed.revision === part.revision`, so `seeded.revision` equals the row's at mount and this PR's starting value is unchanged. Without the guard (master plus this PR), a stale seed is sent with its own revision and fails safe with a 409, so QLT-836-01 becomes defence in depth: fresh values shown before the first save. For `editable` false, the form starts from the seed's real revision instead of the placeholder 0. No save is sent, and it is more correct if the form ever becomes editable without a remount. For the Lead's island, #811 took shape (i) of section 5b, so the clause "the later `/tree` read moves `part.revision` (and `revisionRef`)" no longer applies: it now moves only `part.revision`. Textual merge: clean both ways. The stale comment is QLT-839-05.

**(6) Test adequacy.** The nine unit cases are real reproductions. They drive `usePartValues` against the invented part server, they assert the server's state and not only calls, and S1 covers two fields and all three flushes. Gaps: the own-move case and the E2E case the ruling requires (QLT-839-02), and a case for the identical picture (QLT-839-01). **An E2E case is needed.** The unit harness replaces React's hooks and simulates the tree re-read by mutating a plain object. Only a browser run proves the real wiring: `estimate-workspace.tsx` handing a new `selected` row to a `PartForm` keyed by `part.id`, the real routes' 409 body, and the notice. `estimate-save.spec.ts:294-365` already has the two-tab helper (`saveLength`), so the case is a small addition.

**(7) Security hygiene.** See SEC-839-01.
