## Security and correctness checks

| # | Check | Result |
|---|---|---|
| 1 | **The 24 h window: is any mail lost that should go?** | **Correct.** `sendBefore` = `clock.now()` + 24 h when the row is written (`task-mail.ts:105`). The claim skips a row when `send_before <= now` (`email-outbox-repository.ts:234`), and so does `beginSend` (`:277`, `:284`), so the window is closed at exactly 24 h. Both sides use the process clock (`systemClock`), and in Docker Compose they share one host clock. A transient SMTP failure is retried at +1, +5 and +15 minutes (`retry.ts`), which is far inside 24 h, so retries are never cut short. Two cases lose a mail on purpose, and D-c intends both: a worker outage of more than 24 h, and an assignment made while `FEATURE_EMAIL` is off. Integration covers 23 h 59 min (sent), 24 h or more (skipped as `EXPIRED`, nothing in Mailpit), and a 36 h outage (3 old rows skipped, 1 new one sent) |
| 2 | **The two switches: is any mail written that should not be?** | **Correct.** `queueingEnabled` checks `emailEnabled()` first and reads the settings row only when it is true (`task-mail.ts:84`). `assignTask` reads it before the transaction, as before (`task-service.ts:274`). `reassignTask` reads it inside the transaction, after the withdrawal (`:366`). `loadEmailFeature` is read on each call. That matches the reset-link writer (`composition.ts:173`), and the worker has the same switch (`scheduleMailJobs`: no mail jobs while it is off). A switch turned off after the row is written is still caught at claim time (ALERTS_OFF), which is unchanged. The assign screen's `alertsEnabled` boolean is unchanged (AC-6) |
| 3 | **Withdrawal scope: task and event** | **Exact.** One parameterised `UPDATE` (`email-outbox-repository.ts:211-214`): `status = 'pending' AND event = $event AND starts_with(idempotency_key, $prefix) AND (send_before IS NULL OR send_before > $now)`. The prefix is `task-assigned:<taskId>:`. The trailing colon matters: task IDs are UUIDs, which have no colon, so one task's prefix cannot match another task's key, and no ID is a prefix of another. `starts_with` compares text, so `%` and `_` stand only for themselves, and the integration test proves it with three pattern prefixes. Every value is bound as a parameter, and nothing is joined into the SQL string. The `event` filter adds a second guard. The new row is queued **after** the withdrawal, and its revision is one higher, so it is never withdrawn by mistake |
| 4 | **Transaction and rollback** | **Verified.** `withdrawUnsent(tx, …)` runs inside the reassign's `transactions.run`, after `setAssignment` and `audit.record`. An unknown assigner (`enqueueAssigned` throws) or any later failure rolls the withdrawal back. This is covered by a repository test ("undone with the caller's transaction") and a service-level integration test ("a reassign that fails after the withdrawal puts the old row back", where the row is then sent) |
| 5 | **Race with the worker** | **Safe for `pending` rows; see SQR-02 for one gap.** The claim uses `FOR UPDATE SKIP LOCKED` on the rows it takes. (a) If the reassign's UPDATE locks the row first and has not committed, the claim skips the row, and the next claim sees it expired. (b) If the claim takes the row first, the claim commits `sending` in one statement. In READ COMMITTED, the waiting UPDATE then re-checks `status = 'pending'`, finds it false, and leaves the row alone. So no deadlock and no lost write: the worker's fenced marks (`status` + `attempts`) are never disturbed. The gap is that a row already `sending` when the reassign commits is not withdrawn. It is still sent to the old Engineer at its `beginSend`, and if that SMTP attempt fails, it goes back to `pending` through `markRetry` and is sent to the old Engineer up to about 21 minutes later (SQR-02) |
| 6 | **Privacy (NFR-028, DL-262)** | **Holds.** `expireUnsent` reads and writes only `send_before`. It returns a count, logs nothing, and stores no address. Rows still carry user IDs only (`toUserId` is a UUID in the strict schema), and the addresses are resolved at send time from active users only (`resolveRecipients`). The message body is unchanged, so the NFR-002 cost scan stays at 0 |
| 7 | **Going around `MailService`** | **Nothing missed.** `MailService.enqueue` only passes the call through to `outbox.enqueue(tx, message, clock.now())` (`mail-service.ts:58`): it writes no audit, no log and no metric. So calling `EmailOutboxRepository.expireUnsent` directly skips no side effect. It also avoids `getMailService()`, which builds the transport from `SMTP_*` on first use. The reassign's own audit entry (`task.reassigned`) is unchanged. The withdrawn row itself is the evidence: the claim later marks it `skipped` / `EXPIRED`, and the worker counts it as skipped |
| 8 | **Reassign with e-mail off** | **Correct.** The withdrawal runs whatever the switches say, because the row may date from a time when they were on. No new row is written, and no SMTP variable is needed. Unit and integration tests cover it ("with FEATURE_EMAIL off a reassign still withdraws the unsent row written while it was on, and writes no new one") |
| 9 | **Rows queued before the fix** | **Open: SQR-01.** These rows have `send_before = NULL`, and no code path expires them, except a later reassign of the same task |
| 10 | **Design** | **Sound.** `TaskMail` gets narrow `Pick<>` dependencies (`outbox.expireUnsent` only). `taskAssignedKeyPrefix` sits next to the key builder it mirrors, and it stays out of `idempotencyKeys` so the one-builder-per-event contract test is untouched. No new skip code, no migration for the forward fix, and no DELETE (the runtime role has none). The existing expiry mechanism is reused rather than a second one invented |
