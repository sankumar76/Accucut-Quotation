## Security and correctness checks

| # | Check | Result |
|---|---|---|
| 1 | **Migration: one transaction, enum, nullable, backfill, NOT NULL** | **Holds.** The order is `CREATE TYPE`, then `ADD COLUMN` (nullable), then one `WITH RECURSIVE` `UPDATE ... FROM walk`, then a catch-all `UPDATE ... WHERE node_kind IS NULL`, then `SET NOT NULL`. The file goes to PostgreSQL as one multi-statement script, which runs as one implicit transaction (the same assumption as architecture §4.12 b, "each file runs in one transaction"). So a failure at `SET NOT NULL` leaves the database as before. `prisma migrate diff --exit-code` runs in CI after `migrate deploy` and passed. The column has no default, and the test asserts `is_nullable = NO` and `column_default = null`. `SUB_PART` is refused by the enum (22P02, tested) |
| 2 | **Backfill: the kind derived from the shape** | **Correct and deterministic.** Depth comes from a walk that starts only at `parent_id IS NULL`. Each row has one parent, so the reachable set is a forest: no row is visited twice and the recursion ends. Depth 1 gives `MAIN_ASSEMBLY`. Depth 2 with at least one child (a correlated `EXISTS` served by `idx_estimate_nodes_parent_id`) gives `SUB_ASSEMBLY`. Everything else gives `PART`. The trigger keeps a parent in the same estimate, so the global walk is the per-estimate walk. No `FASTENER` is produced (asserted). The test's expected kinds come from an **independent** walk of the fixture, not from the SQL. It covers a branch to depth 4, a depth-2 leaf, two top rows, a 500-node six-level `tree500`, an empty estimate and a single top row |
| 3 | **Unreachable rows become PART** | **Holds.** A two-row cycle (the schema refuses only a self-parent) is not reached by the walk and gets `PART`, so `NOT NULL` cannot fail the release (tested). Those rows are not shown, and Calculate already refuses a tree with an unreachable row (`checkedPartsOf`), so labelling them `PART` changes nothing a person sees |
| 4 | **No data loss; deep legacy trees** | **Holds.** The `UPDATE` writes only `node_kind`. The only `estimate_nodes` triggers are `BEFORE INSERT OR UPDATE OF parent_id, estimate_id` and `OF image_id, estimate_id`, so neither fires. The test snapshots every other column of every row (id, estimate, parent, place, inputs, image, revision, `created_at`, `updated_at`) and every `estimates` row before and after: equal. | 6 | **Add: `{ parentId, nodeKind }` against `ALLOWED_CHILDREN`, on the server** | **Holds.** The body is strict (`parentId` required and nullable, `nodeKind` from `NODE_KINDS`). Every refusal is thrown before the insert, inside the transaction, so nothing is written (tested on real tables for all 20 parent and kind pairs). The check reads the parent under the estimate's row lock, and every structure change takes that lock, so the parent cannot be deleted between the check and the insert. The server and the browser import the same frozen table from `src/lib/estimate/node-kinds.ts`; nothing in the client decides |
